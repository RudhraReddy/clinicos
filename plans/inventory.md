# Inventory

**Status:** Implemented

## Overview
Manages the clinic's drug and product stock using a two-layer model: `ProductMaster` (catalog — name, category, GST, min stock) and `InventoryBatch` (physical stock — quantity, expiry, MRP, purchase price, batch number). Every stock change is audit-logged via `InventoryHistory`. The feature supports viewing stock, editing master and batch records, exporting to CSV, importing from CSV, and viewing purchase invoice history.

## Affected Layers
- DB models: `ProductMaster`, `InventoryBatch`, `InventoryHistory`, `PurchaseInvoice`
- Backend routes: `Backend_db/routes/inventory.py` (blueprint `inventory`, prefix `/api`)
- Frontend pages/components:

  - `frontend/app/inventory/invoice_edit/page.tsx` (invoice editing)

  - `frontend/components/DataTableColumnFilter.tsx` / `DataTableRangeFilter.tsx` (filter widgets)

## Data Flow

### Viewing Stock
1. `GET /api/inventory` returns all `ProductMaster` items with aggregated stats (total qty, min/max MRP, earliest expiry, status tags, active vendors) computed via SQL aggregates across `InventoryBatch`.
2. Status tags are computed server-side: `OUT OF STOCK` (qty ≤ 0), `LOW STOCK` (qty < min_stock_level), `EXPIRED` (earliest expiry month/year ≤ current), `EXPIRES SOON` (≤ 3 months to expiry), `OK` (none of the above).
3. The inventory page applies client-side multi-column filtering (name, manufacturer, vendor, category, status, ID, quantity range, price range, value range, expiry, pack size, GST, HSN, min stock range) over the loaded data.

### Viewing Batches
1. Clicking a product row opens `ViewBatchesDialog`, which calls `GET /api/inventory/<id>/batches` (active batches only, quantity > 0).
2. Individual batch fields (expiry date, quantity, MRP, purchase rate, GST rate) can be edited inline via `PUT /api/inventory/batch/<id>`. A quantity change creates an `InventoryHistory` record with `type='ADJUSTMENT'`.

### Editing Master Items
`PUT /api/inventory/<id>` updates `item_name`, `category`, `min_stock_level`, `pack_size`, or `hsn_code` on the `ProductMaster` record.

### Adding a Master Item (no stock)
`POST /api/inventory` creates a new `ProductMaster` with no associated batches.

### CSV Export
`GET /api/inventory/export` streams a CSV file with one row per `ProductMaster`, including aggregated total qty, avg purchase rate, max MRP, and earliest expiry.

### CSV Import
`POST /api/inventory/import` (multipart, with `mode` form field):
- `mode=update` (default): Each CSV row creates a new `InventoryBatch` with the given quantity, and logs a `PURCHASE` history entry. A synthetic `PurchaseInvoice` with `source='CSV_UPDATE'` is created for the import run.
- `mode=overwrite`: Computes the difference between the CSV target quantity and the current total on hand. Creates an adjustment batch for the diff and logs an `ADJUSTMENT` history entry. A synthetic `PurchaseInvoice` with `source='CSV_OVERWRITE'` is created.
- Products are matched by normalized `item_name` (case-insensitive) and optionally `pack_size`. New products are auto-created if no match is found.

### Searching Inventory (for Billing)
`GET /api/inventory/search?q=` searches `item_name`, `manufacturer`, `generic_tags`, and product `id` (up to 20 results). Returns aggregated qty and max MRP per product.

## Business Rules
- `ProductMaster` never stores quantity or price directly — all stock data lives in `InventoryBatch`.
- A product's total quantity is always computed via `SUM(InventoryBatch.quantity)` where `quantity > 0`.
- `ProductMaster.id` is a 6-char uppercase hex string generated by `secrets.token_hex(3).upper()`.
- Expiry status is checked at month granularity, not day: a batch is considered expired if `today.year > expiry.year OR (today.year == expiry.year AND today.month >= expiry.month)`.
- The inventory list endpoint calculates `total_value` as `max_mrp * total_qty` — this is an approximation, not an exact stock valuation.
- Manual batch edits that change quantity create an `InventoryHistory` entry with `type='ADJUSTMENT'`.
- Price-only batch edits (MRP, purchase_rate, GST) do not create history entries.

## API Endpoints
| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/inventory` | List all products with aggregated stock data |
| POST | `/api/inventory` | Create a new master product (no stock) |
| PUT | `/api/inventory/<id>` | Update master product fields |
| GET | `/api/inventory/<id>/batches` | List active batches for a product |
| PUT | `/api/inventory/batch/<id>` | Update a specific batch (qty, expiry, MRP, rate, GST) |
| GET | `/api/inventory/search` | Search products by name/manufacturer/tags/id (max 20) |
| GET | `/api/inventory/export` | Download full inventory as CSV |
| POST | `/api/inventory/import` | Import/update stock from CSV |
| GET | `/api/inventory/invoices` | List all purchase invoices |
| GET | `/api/inventory/invoices/<invoice_number>` | Get invoice details with batch items |
| GET | `/api/inventory/invoices/<invoice_number>/image` | Serve stored invoice image file |
| GET | `/api/inventory/invoices/<invoice_number>/export` | Download invoice as CSV |

## Known Constraints / Risks
- There is no endpoint to delete a `ProductMaster` or `InventoryBatch` record.
- CSV import with `mode=overwrite` has a potential bug: the `InventoryHistory` entry is created before `db.session.flush()`, so `batch.id` may be `None` at the time the history record is written.
- The `total_value` returned by the list endpoint uses `max_mrp * total_qty`, which overestimates value for products with multiple batches at different MRPs.
- On Render (production), `UPLOAD_BASE_DIR` is `/tmp/clinic_uploads` which is ephemeral — invoice images and patient images are lost on instance restart.
- The inventory search endpoint does not filter by `quantity > 0`, so out-of-stock items appear in billing search results (the frontend shows "Out of Stock" but still allows adding to a bill).
