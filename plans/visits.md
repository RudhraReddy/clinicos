# Visits

**Status:** Implemented

## Overview
Records and tracks patient visits to the clinic. Each visit is linked to a patient and carries a status, a reason, visit date/time, visiting fee, and payment information. Visits serve as the linking record between a patient and any bills or prescriptions created during that encounter.

## Affected Layers
- DB models: `Visit`
- Backend routes: `Backend_db/routes/visits.py` (blueprint `visits`, prefix `/api`)
- Frontend pages/components:
  - `frontend/app/visits/page.tsx` (visit list + add-visit dialog)
  - `frontend/app/visits/[id]/page.tsx` (visit detail view)
  - `frontend/components/AddVisitDialog.tsx`
  - `frontend/components/EditVisitDialog.tsx`
  - `frontend/components/VisitsTab.tsx` (all-visits table, embedded in other pages)

## Data Flow
1. User opens `/visits`. The page simultaneously fetches `GET /api/visits` (latest 50) and `GET /api/patients` (latest 50) to populate the visit table and the patient selector dropdown.
2. To create a visit, the user selects a patient from the dropdown and submits the form. `POST /api/visits` is called with `patient_id` and `visit_date` (required) plus optional `visit_time`, `reason`, `status`, `visiting_fee`, `amount_paid`, `payment_status`.
3. The backend generates a `visit_id` via `generate_visit_id(patient_id)` (in `Backend_db/utils.py`) and persists the record.
4. Clicking a row in the table navigates to `/visits/<visit_id>`. That page calls `GET /api/visits/<visit_id>` to fetch and display the visit record.
5. Status, reason, fee, and payment fields can be updated in-place via `PUT /api/visits/<visit_id>`.
6. A visit can be deleted via `DELETE /api/visits/<visit_id>`.

## Business Rules
- `patient_id` and `visit_date` are required to create a visit.
- Default `status` is `'in_progress'`. Valid status values observed in code: `'in_progress'`, `'done'`, `'cancelled'`.
- When a bill is created and linked to a visit (via `visit_id` in the billing payload), the backend automatically sets `visit.status = 'done'` and sets `visit.invoice_id` to the new invoice ID.
- `payment_status` defaults to `'unpaid'`. Valid values: `'full'`, `'partial'`, `'unpaid'`.
- `visiting_fee` defaults to `0`; `amount_paid` defaults to `0`.
- `visit_id` format is `<patient_id>-DDMMYY-XXX-XXX` (generated by `utils.generate_visit_id`).
- The list endpoint (`GET /api/visits`) returns at most 50 visits, ordered by `created_at` descending.
- The per-patient list (`GET /api/visits/patient/<patient_id>`) returns all visits for that patient ordered by `visit_date` descending.

## API Endpoints
| Method | Path | Description |
|--------|------|-------------|
| POST | `/api/visits` | Create a new visit |
| GET | `/api/visits` | List recent visits (max 50, newest first) |
| GET | `/api/visits/patient/<patient_id>` | List all visits for a specific patient |
| GET | `/api/visits/<visit_id>` | Get full details of a single visit |
| PUT | `/api/visits/<visit_id>` | Update visit fields (partial update) |
| DELETE | `/api/visits/<visit_id>` | Delete a visit record |

## Known Constraints / Risks
- Deleting a visit does not cascade to linked `Bill` records or `PrescriptionItem` records — orphaned data will remain.
- The `visits` list page loads both visits and patients in parallel on mount. If the patient list exceeds 50 records, the patient selector dropdown will be incomplete.
- The visit detail page (`/visits/[id]/page.tsx`) currently only displays status and reason — visiting fee, payment status, and other financial fields are fetched but not rendered.
- There is no server-side validation preventing a visit's `status` from being set to an arbitrary string.
